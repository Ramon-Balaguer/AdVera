# Feature: Summary output language selection regression
Status: complete
Last updated: 2026-09-26

## Objective

Prevent a completed Summary extraction generated under another output-language preference from being shown for the current preference.

## Scope

Filter the current Summary job by the persisted `es` or `en` output language and prompt version while preserving transcript hashes, historical jobs and worker propagation. Catalan output detection and transcript translation are out of scope.

## Acceptance criteria

- A current Spanish preference never returns a Summary job stored for English, and vice versa.
- A historical job in another language does not block scheduling a new job for the current language.
- Repeated requests with the same transcript and output language remain idempotent.
- The definitive transcript remains the only Summary input source.
- A prompt change that strengthens output-language instructions does not reuse an extraction generated by the previous prompt version.

## Implementation state

Implemented. Summary status lookup now includes the current output language and prompt version in its job selection, and the provider explicitly separates output language from transcript language.

## Decisions

- Keep output language frozen on each `SummaryJob` as defined by [ADR 0009](../adr/0009-summary-output-language-provenance.md).
- Do not delete or mutate historical extractions.
- Do not add a migration; the language column and provenance contract already exist.

## Files changed

- `backend/app/summary_jobs.py`
- `backend/app/summary_api.py`
- `backend/tests/test_summary_worker.py`

## Validation

- Focused Summary prompt and worker tests pass.
- Regression coverage verifies that an English lookup does not return a Spanish job.

## Risks and next action

The provider prompt currently supports Spanish and English only. If this meeting was generated in Catalan despite a Spanish job language, inspect the stored `SummaryJob.language` and provider response from that historical run separately.
